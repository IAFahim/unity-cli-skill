# Burst / ECS performance: recipes, wins, dead ends

Verified on Unity 7000.0.0a16, Entities 6.7.0, Burst 1.8.25, Ryzen 5 8500G (6C/12T, DDR5), 11 job workers. Numbers are medians of 5 fresh editor processes unless marked.

## Measuring honestly

- Editor batch runs compile Burst jobs with safety checks on by default. Set `BurstCompiler.Options.EnableBurstSafetyChecks = false`, `JobsUtility.JobDebuggerEnabled = false`, `NativeLeakDetection.Mode = NativeLeakDetectionMode.Disabled` at the top of the `-executeMethod`, before any job, and log them with every result. Tl 4M entities x4 kind fixture: 41.2 ms/tick [40.3-43.0] with them off (tl.unity 3b44b20) against about 52.9 ms with editor defaults on the same kind job (earlier harness): compare arms only under identical settings.
- Prove a generated job you cannot edit ran under Burst: call a `[BurstDiscard] static void Mark() { Hits = 1; }` (managed static) from a user method the job inlines (a feeder/Evaluate), and fail the run if `Hits != 0` after timing. Burst drops the call; a managed fallback sets it.
- Memory floor of a job: a Burst `IJobChunk` with read-only handles that sums exactly the bytes the job reads (enable bits, buffer headers and used elements, columns), timed the same way (schedule + complete, 32 steps). Tl kind job at 4M x4: touch 15.5 ms vs kind job 26.3 ms (59 %), so roughly 10 ms is compute above the floor; at 10k x150 it is 0.55 vs 2.15 ms (compute-bound).
- Bytes per entity: `archetype.ChunkCapacity` and `TypeManager.GetTypeInfo(type.TypeIndex).SizeInChunk` over `archetype.GetComponentTypes(Allocator.Temp)`; a buffer's SizeInChunk is header 16 B + inline capacity x element size. Tl scale archetype: 320 B/entity, 49 per chunk, of which `TimelineRequest` inline (8 x 16) is 128 B the kind job never reads.
- Before a Unity run, diff what a generator change emits: `dotnet Tl.Gen.Unity.Snapshot.dll <pkg>/Core <domain dir> <out> <AssemblyName>` emits the jobs for any domain folder in seconds (tl.unity `Tools~/Tl.Gen.Unity.Snapshot`).

- Cache per-entity derived state across ticks without user cooperation (Entities 6.7, tl.unity perf/s4-unity-horizon): in an `IJobChunk` read `chunk.DidChange(ref playbackRW, LastSystemVersion)` BEFORE the first RW accessor call (that call bumps the version) and clear the chunk's cache when true. The system's own writes from its previous update never trip it; a `EntityManager.GetBuffer<T>(e)` RW access from outside between updates does, even without a value change (PlayMode test, 7000.0.0a16). Do the clear before any idle early-out, or a chunk skipped while idle keeps a stale cache. Keep the cache column optional (`chunk.Has`) so existing archetypes stay on the reference path.

- Change versions (Entities 7.0.0 built-in, probed with a filtered `IJobChunk` per tick, sv V0): `GetRequiredComponentDataPtrRW` bumps the chunk's version even when nothing is written; `...PtrRO` never does; a `ComponentLookup` write (`lookup[e] = v`) bumps only the written chunks; enable-bit writes (`lookup.SetComponentEnabled`, `chunk.SetComponentEnabled(ref h, i, b)`, `chunk.GetEnabledMask(ref h)[i] = b`) bump only the enableable component's version; a system's own RW access never trips its own `DidChange(ref h, state.LastSystemVersion)` next update. A Tl generated kind job takes RW pointers to every writable column of any chunk with a live kind, so a DidChange filter behind it sees false positives, never misses.
- Manual-world probe harness without the default world: `[DisableAutoCreation] partial struct S : ISystem` with public config fields, `var h = world.CreateSystem<S>()`, set fields through `ref world.Unmanaged.GetUnsafeSystemRef<S>(h)`, tick with `h.Update(world.Unmanaged)`. `[BurstCompile(CompileSynchronously = true)]` on every job makes even the first launch of a fresh project run Burst (all `[BurstDiscard]` probes 1).

- Untyped columns in Burst (Entities 7.0.0 / Collections 7.0.0 / Burst 2.0.0, the 7000.0.0a16 built-ins; sv adapter v3): a library that must not know the game's component types takes `state.GetDynamicComponentTypeHandle(ComponentType)` and uses `chunk.GetDynamicComponentDataArrayReinterpret<int>(ref h, 4)` (+ `NativeArrayUnsafeUtility.GetUnsafePtr`), `chunk.DidChange(ref h, version)`, `chunk.Has(ref h)`, `chunk.GetEnableableBits(ref h)`, `chunk.SetComponentEnabled(ref h, row, b)`, `chunk.IsComponentEnabled(ref h, row)`; all compile and run in Burst. Untyped writes by entity: `state.GetEntityStorageInfoLookup()`, `info.Chunk` + `info.IndexInChunk`, then the same reinterpret (RW, bumps that chunk's version). A fixed set of handle fields (no arrays of handles) works; fill unused slots with a real handle (e.g. read-only of a component every chunk has) and call `.Update(ref state)` on every slot each tick, or the first structural change throws "...DynamicComponentTypeHandle ... has been invalidated by a structural change". A scheduled `IJob` that only used dynamic handles later broke world teardown ("previously scheduled job ... You must call JobHandle.Complete()") although its dependent handle was completed; running that small job with `.Run()` removed it (root cause not found).
- A managed main-thread host (sv's `Board`) behind an `ISystem`: store `GCHandle.ToIntPtr(GCHandle.Alloc(host))` in an unmanaged singleton, read it in `OnCreate` with `state.GetEntityQuery(...).GetSingleton<T>()`, and resolve it in a non-Burst `OnUpdate` with `GCHandle.FromIntPtr(p).Target` (0 B per frame). Create such systems after the singleton exists (`[DisableAutoCreation]`, `world.CreateSystem<T>()`, `group.AddSystemToUpdateList`, `SortSystems`).
- Test a library against a real Tl generated kind job without a SubScene: game asmdef with `[TlState]` columns, `[TlKind]`, `[TlClip]` and a track (`versionDefines` on `com.tl.unity` + that define in `defineConstraints`, so the test compiles out without Tl), a `TimelineAsset` built in code with `TlTrack`/`TlClip` and the generated `<Ns>_<Clip>_TlData`, bake with the internal `BakingUtility.BakeGameObjects` by reflection, then update `TlLibrarySystem`, `TlTimelineRegisterSystem`, `TlPlayOnAwakeSystem`, `TimelineKindTickSystem` and `TlKindSystem<Tl.Generated.TlAuto_<Asm_With_Underscores>_Jobs>` by hand. A clip at 0.5 s for 0.5 s feeds ticks 30-59.
- `GC.GetTotalAllocatedBytes` is missing from the Unity editor's netstandard profile (CS0117) though the CoreCLR runtime has it: `(Func<bool,long>)Delegate.CreateDelegate(typeof(Func<bool,long>), typeof(GC).GetMethod("GetTotalAllocatedBytes", new[] { typeof(bool) }))`.
- A per-asmdef `csc.rsp` with `-nullable:enable` next to an embedded package's asmdef takes effect on 7000.0.0a16 (0 CS8632 warnings for sources full of `?`).

- Cross-host identity of a .NET Tl scenario in Unity without a SubScene (tl.unity aeb87e9, sv NorthStar2, verified bit-equal at `JobsUtility.JobWorkerCount` 1 and 11): copy the .NET kinds file into an editor asmdef with the same namespace (kind keys hash full type names, not assemblies), bake the same `TypedTimeline`s in the editor with the vendored `Tl.Gen.Tlb.LibraryBake` + `Tl.LibraryAssembler.Assemble(parts, 60, LibrarySettings.Default)`, load with `TlLibrary.FromBytes(bytes).Publish(manager)`, add the systems with the private `TlSceneRun.AddSystems(world)` (reflection), spawn entities like `TlSceneRun.Spawn` (Playback, TimelineRequest, TimelinePlaying, TimelineHorizon, the `[TlState]` columns, each kind's Entry/Active/Enabled with Active and TimelinePlaying disabled), start with a `TimelineRequest { Slot = -1, Op = RequestOp.Start }`, set the `TimelineStep` singleton, then `group.Update()` per tick. `JobsUtility.JobWorkerCount` can be set at run time for worker sweeps. Tl's Burst probe is `TimelineKindTick.ManagedRuns` on a system entity: query it with `EntityQueryOptions.IncludeSystems`. In a test, write `global::Tl.Unity.Playback` (`Tl.Playback` also exists).

## Measured wins

- Gate after a generated-job change (tl.unity b4d70b3): a test added under `Tests/Kinds/Tests` runs in PlayMode, not EditMode (that asmdef is a runtime test assembly); counts packs 87/72, default 71/72 on the warm second run; the cold first run fails only the Burst-ran-managed assertions (8 packs, 7 default).

- Replace a per-entry search over library tables with a precomputed direct pointer when the build can prove it returns the same answer (tl.unity c922218, `KindIndex.StepInWindow`: one step pointer per window that lies in one stage of a timeline with ascending stage ends; otherwise the old stage search). Tl kind job 4M x4: 25.7 -> 21.6 ms (-16 %), 10k x150: 2.04 -> 1.67 ms (-18 %), hashes identical. Dependent loads per entry, not arithmetic, were the cost; the gain shrinks as the job nears its memory floor (touch job 14.5 ms).

- Skip per-row rule work between known edges ("horizon glide", tl.unity perf/s4-unity-horizon 9f8dccb, tl d0b77476): a 1-byte per-row count of steps until the next edge, recomputed only at edges, turns the Tl kind tick into `tick += dir` for 4 slots. Tick job 4M x4: 14.1 -> 10.3 ms (D=3000) and 14.5 -> 10.0 ms (D=300); 10k x150: 1.08 -> 0.45 ms; totals 40.7 -> 36.9 / 40.7 -> 36.4 / 2.93 -> 2.27 ms, hashes identical, 0 B main thread over 1000 ticks. The 4M job stays ~10 ms with every row gliding because it still reads and writes every 48 B in-chunk playback buffer: it is near the memory floor, so only not touching the bytes (deferred ticks) would go lower. Plan projections of 6-8 ms ignored that floor; measure a touch job first.
- S4+S5 together (tl.unity perf/int-unity, tl d0b77476; 5 procs ABAB, safety off): 4M x4 D3000 38.15 -> 31.40 ms (1.22x; tick 14.0 -> 9.9, kind 24.9 -> 22.0), D300 39.80 -> 31.74, 10k x150 2.87 -> 1.94 (1.48x); with editor-default safety 48.4 -> 39.1 (1.24x). A second agent's rerun from fresh clones (aeb87e9 + harness vs 3b44b20 + harness, own probe, fixtures rebaked with both tl pins: byte-identical) read 37.77 -> 31.25 (1.21x), D300 1.25x, 10k x150 1.44x, same hashes: the old arm is stable across sessions to ~1 %, the 10k ratio to ~3 %. The two wins add (tick and kind are separate jobs), but neither reaches 2x: both jobs sit near their memory floor. Shrinking the kind's inline capacity to its p99 occupancy (user const `KindCapacity.<Kind> = 4` instead of 128 B / 12 B = 10) cut 4M x4 a further 13.8 % (31.15 -> 26.85, tick too: fewer chunks) and 370 MiB, and does nothing at 10k x150; it is a fixture knob, so give the old arm the same capacity before quoting a ratio.
- A setup cost to watch: a derived per-library table built in managed code at bind (2 bytes per timeline tick, 6 MB for 1000 x 3000) plus the extra column raised ready setup 624 -> 685 ms at 4M x4.

- Memory-floor and atomics numbers (sv V0, 11 workers, safety off, 3 processes, ~316 B entities, 48/chunk): a RO touch of 24 B/row reads 1M rows in 0.77 ms and 4M in 3.3 ms (29-33 GB/s); a clamp-and-clear fold of 2 int columns 1.38 / 5.74 ms; a `DidChange`-filtered pass that skips every chunk still costs 0.12 ms at 21,846 chunks (~5 ns/chunk). `ComponentLookup` writes from one Burst `IJob`: 8.5-10 ns each in entity order, 25-44 ns in random order (10k / 1M writes), ~4 us fixed for 128. `Interlocked.Add(ref p[i], 1L)` on a 64 B-aligned `long*` in an `IJobParallelFor` costs the same as a plain random `+=` (0.75 ms per 1M sends, exact); all sends to one target serialize at ~10.4 ns each (1M sends 11 ms).

- A shared reference loop with per-row null tests of optional pointers (`word.Floor == null ? constant : BoundOf(word.Floor[row])`) is not unswitched by Burst 2.0: sv's `Fold.Word` over 1M rows x 2 int columns in an `IJobChunk` took 3.8 ms; the same law as one loop per bound strategy (pointer vs constant chosen once per chunk), bits unchanged, took 1.6 ms (11 workers, safety off). Keep the scalar reference for tests and dispatch to strategy loops in hot jobs; prove equality with a pinned digest, not by reading the loop.
- Measure the bench host before blaming the library: Burst probes can all read 1 while the main-thread stage still climbs cell after cell; sv's `Board` leaked freed sets (Apply + Recalculate 0.3 -> 20 ms over 10 cells of add/remove churn) until fixed. Build a fresh world per bench cell, or run each cell twice and compare.
- Dual-target `netstandard2.1` + `net10.0` compute libraries on Unity 7 (verified 7000.0.0a16, CoreCLR + IL2CPP, Burst 2.0.0, i9-14900K):
  - **Coarse sidecar over fine P/Invoke**: Unity 7 CoreCLR runs `.NET 10` RyuJIT (`Avx2` + `AvxVnni`), whereas Burst 2.0.0 on x64 stops at AVX2/FMA (`vpdpbusd` absent; `vpmaddubsw + vpmaddwd` ceiling). Routing whole multi-layer worker steps through a single coarse `[UnmanagedCallersOnly(CallConvs = new[] { typeof(CallConvCdecl) })]` sidecar entrypoint instead of per-op function pointers eliminated ~1,500+ unmanaged crossings per token (`-30 us/tok` at 8 threads), bringing CoreCLR player speed to parity with native `.NET 10 NativeAOT` (`368 us/tok` vs `368 us/tok`).
  - **Gate `[BeforeSceneLoad]` Burst installers**: With no domain reload and eager `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` hooks, Burst installers can silently claim active kernel tables before lazy `.NET 10` sidecars resolve (via `LoadFromPath` when `Assembly.Location` is empty), and secondary row-op installers can append onto or overwrite an active sidecar. Guard secondary installers on `IsInstalled`/sidecar priority first.
  - **Key multi-threaded split flags off function pointers, not `#if`**: On `netstandard2.1` plugin builds where compile-time `Simd.Enabled` evaluates `false`, capability checks like chunk/position splitting stay disabled even when Burst or a native sidecar installs vector kernels. Check whether the active kernel table pointer (`!= 0`) is installed instead (~25-28% faster prefill and ~12-14% faster decode on IL2CPP + CoreCLR).
  - **Eliminate Burst `@plt` calls and per-iteration `stackalloc`**: `objdump -d` over `lib_burst_generated.so` showed `[BurstCompile]`-to-`[BurstCompile]` calls and non-inlined helpers emit intra-assembly `@plt` thunks (forcing stack arguments, YMM caller-saves, `vzeroupper`). Move bodies into `[MethodImpl(MethodImplOptions.AggressiveInlining)]` `*Impl` helpers called by thin `[BurstCompile]` wrappers (`0` user `@plt` verified), and hoist `stackalloc` outside token loops to avoid stack growth and `.locals init` `burst.memset` overhead.

## Dead ends and traps

- LLVM in Burst 2.0.0 (7000.0.0a16, AVX2 target) does not auto-vectorize a loop that gathers, with or without a mask. `Loop.ExpectVectorized()` then fails with `BC1321`, for a branch-free lane loop with `cond ? p[i] : 0` loads too. A Burst compile error in a batch run does not stop the run: the job silently runs as managed C# and gives plausible but 1.7x slower numbers. Gate every bench on `grep -c 'error BC' log` = 0 before printing results. Also, 8 scalar `vmovss` stores followed by one 256-bit load of the same array stall store forwarding (19 % of a kernel's samples).
- A batch log line `Requested script compilation because: AssetDatabase observed changes` before your `-executeMethod` starts is the normal startup compile after a source change. Only one after your method's first output line means a reload during the run.

- Mono float bits: Unity's bundled MonoBleedingEdge 6.13 (`<Editor>/Data/MonoBleedingEdge/bin/mono.exe`, JIT, also `-O=float32`, `-O=-all`, `--llvm`) keeps float intermediates wider than float32: a chained add/multiply stat fold over 1M random sets differed by 1-2 ulp in 5.9 % of sets from .NET 10, the Unity 7 editor (CoreCLR) and Burst `FloatMode.Strict`/`Default` (all equal, and equal to a strict IEEE reference). Writing `(float)(a + b)` on every operation makes Mono bit-equal. `FloatMode.Fast` differs. Run such legs by compiling with `mono.exe <..>/lib/mono/4.5/csc.exe -unsafe+ -optimize+` and running the exe with `mono.exe`; `--interpreter` segfaulted. NaN payload/sign bits differ between hosts even when values agree: canonicalize NaN before hashing.

- Copying job fields (a pointer-table struct, a bool) into locals once per chunk inside a Burst `IJobChunk` gave -1 % at 4M x4 (inside noise, reverted by the 3 % kill rule) and -3.5 % at 10k x150 (tl.unity 72fe89f): Burst already keeps them in registers; do not expect hoisting to pay. Exception, opposite per compiler: hoisting a repeated address computation through a call (`RunOf(e)` once per row instead of `SlotOf(e, slot)` per entry) paid 1.2-1.45x in Burst (tl.unity #38) but 0.98-1.025x in RyuJIT .NET (tl#600, KindSystems smoke, 6 interleaved runs): measure each host separately, a win in one is no evidence for the other.
- An A/B session's old arm drifts by 3-4 % between sessions (kind job 25.9 vs 24.9 ms, same code): normalise each new-arm median by the same session's old arm before judging a 3 % kill rule.

- `BurstCompilerService.GetDisassembly(MethodInfo, options)` (Unity 7: in `UnityEngine.BurstModule`, reachable by reflection) on `JobChunkProducer<T>.Execute` with hand-written options `--dump=Asm --float-mode=Strict ...` returns "Unable to compile method in BurstCompilerService::CompileAsync" instead of throwing; build the options with Burst's own internal `BurstCompiler.Options.TryGetOptions(jobType, out string, ...)` instead (Burst Inspector does this).
- Typed `BufferAccessor<T>` (Entities 6.7) exposes only `this[]` and `Length`; raw `GetUnsafePtrAndLength(index, out length)` exists only on `UnsafeUntypedBufferAccessor` (needs a `DynamicComponentTypeHandle`). With safety checks off a `DynamicBuffer` per row is just a header pointer, so "raw runs" has little to remove.
- Lane-first (skip frame work when a baked fold lane exists) and row-major multi-kind passes cannot help a fixture whose feeders have no `Fold` and whose job has one kind: check the generated job first (Snapshot tool); if it is byte-identical the gain is 0 by construction.
- Hybrid CPU P-core affinity on Linux CoreCLR standalone players: on hybrid x64 machines (e.g. 8 P-cores + 16 E-cores), unpinned `T=8` CoreCLR player runs hit heavy E-core/SMT scheduler tail spikes (`12.95 ms` prefill / `462.48 us` decode medians vs `2.596 ms` / `368.95 us` med when pinned to the 8 physical non-HT P-cores via `taskset -c 0,2,4,6,8,10,12,14`). Benchmark both pinned P-cores and unpinned so OS placement noise is not misattributed to kernel regressions.
- Unaligned `Vector256` vector tails over scratch buffers: never overrun the logical slice length with full 8-float `Vector256<float>` loads into reused or padded scratch arenas; finish accumulate and combine passes with an explicit `<8`-float scalar tail so residual arena values cannot corrupt results.
- Single hoisted aligned `stackalloc` per prefill token & `netstandard2.1` capability gating: combine small per-block temporaries into one 32-byte-aligned `stackalloc` at token scope to avoid repeated stack/alignment work, and gate multi-threaded chunking on populated native/Burst function-pointer slots rather than compile-time `netstandard2.1` SIMD flags that evaluate `false` while Burst or sidecar kernels are installed.
- A per-row kind tick that reads and writes every playback slot is memory-bound at scale: tl.unity's `KindTickJob` at 20,000 rows x 200 slots (32 MB of 8-byte slots) took 2.5 ms per tick on 11 workers whatever the per-slot rule cost, and one cached horizon per row (S4 glide) was 0.85-1.6x because with 100-200 slots some slot is almost always due. Only not touching calm slots helps: store a monotone value relative to a per-row clock (`tick - clock`, `+ clock` when the slot runs backwards, so a world direction flip needs no re-encoding), keep a `ushort` due per slot in a parallel `DynamicBuffer`, and let the row's byte horizon count ticks to its next due slot. Tick job 1.4x (120-tick loops) to 10x (3000-tick loops); the remaining cost at short loops is the kind events themselves (entry buffer appends and removes), which both paths do (tl#647 A3, tl.unity PR 40).
- Benchmark harness trap: `Stopwatch.StartNew()` inside a timed loop allocates 40 B per call on the main thread; use `Stopwatch.GetTimestamp()` deltas when the same run also asserts 0 B warm allocation.
- Adding a required handle to a public `IJobChunk` struct breaks every caller that builds the job itself (tests too): an unassigned `ComponentTypeHandle` throws "has not been assigned or constructed" at schedule time. Grep for `new <Job>` before adding a field.
- Profile Burst jobs with Linux `perf` at `perf_event_paranoid=2` (no sysctl change): `perf record -F 1999 -o out.data -- <Editor>/Unity -batchmode ... -executeMethod <bench>` samples user space; `--call-graph=fp --user-callchains` adds call chains (`-g` alone fails). The Editor's Burst JIT objects in `Library/BurstCache/JIT/*.so` keep symbols and line tables, so `perf annotate -s '<symbol>'` prints the C# source next to each hot instruction; the profile includes import and compile time, so judge only job symbols (tl.unity A3, 7000.0.0a16).
- Decompose a generated job before optimising it: a `SharedStatic<int>` selector read inside the job switches off one cost at a time (slot read, clip data, user call) in one compile. tl.unity's kind job at 20,000 rows x 200 slots spent 1.23 of 2.22 ms reading one random `Playback` slot per active clip; caching the slot's stored tick and flag bits in spare entry bytes, refreshed by the tick job, cut the kind jobs to 1.14 ms bit-exactly. Prefetching the slots or resolving a row's library steps in a tight first pass did not help (memory latency was in the slot read, not the step chain).
- A job can trust data another job derived this frame by comparing `chunk.GetChangeVersion(ref handle)` with the producer's `state.GlobalSystemVersion` (written by the producer job itself, not the main thread, so a still-running consumer of the previous frame never races it). Any later system's write has a higher version. An `EntityManager` write made between two hand-driven system updates gets the earlier system's version and is not seen (7000.0.0a16).
- `chunk.GetEnabledMask(ref DynamicComponentTypeHandle)` once per chunk, then `mask[row] = value`, replaces per-row `chunk.SetComponentEnabled` (two archetype lookups, a CAS loop, a `lock add` and a version store per call) with a plain bit store plus an atomic add only when the bit flips; get it lazily so untouched chunks keep their version.
- A self-hosted CI runner on the same machine can share the default probe project (`~/.cache/<repo>-probe-<version>`) and rewrite its manifest between your runs; benchmark from a private copy (`cp -a` the probe, point its manifest at your worktree) and push only after measuring, since a push starts the runner's Unity on the same cores.
- A second-agent rerun of tl.unity's lazy kind rows (IAFahim/tl#647 A3, `3e55928`) from a fresh clone and fresh `-createProject` matched every owner-scale eager/lazy speedup within 8 %, and its review found a pre-existing gap the main tests missed (a row keeping `TimelineClock` but losing `PlaybackDue` was never decoded). Brief reviewers with the invariant to break, not just the diff. `OwnerScaleBench` prefixes its lines `TlOwnerBench: cell`, so grep `cell `, not `^cell`.
- A small `public` lookup called once per buffer element from generated Burst jobs is not inlined when it contains a call to a slow path; mark the fast path `[MethodImpl(MethodImplOptions.AggressiveInlining)]` and move the slow path into a `NoInlining` method. tl.unity's `KindIndex.StepInWindow` this way made the kind jobs 10 % faster at 20,000 x 200 (7000.0.0a16, Burst). Moving a 25-entry kind buffer inline into the chunk (`InternalBufferCapacity` 2 -> 32) gave only 3 %: once per-row data is cached, the pointer hop to the heap is not the floor.
- BovineLabs Core 2.0.0-pre.8 (MIT) reaches Entities internals on 7000.0.0a16 through an `.asmref` to the built-in `Unity.Entities` asmdef (GUID `734d92eba21c94caba915361bd5ac177`), which `UnityEngine.EntitiesModule` grants internals to: verified on 7000.0.0a16 (a probe `Assets` folder with `Unity.Entities.asmref` holding `{"reference": "GUID:734d92eba21c94caba915361bd5ac177"}` compiled `typeof(ChunkDataUtility)` with 0 errors into `Library/ScriptAssemblies/Unity.Entities.dll`). It ties a package to Unity's internals; for tl.unity it would save about 0.01 ms, so it was not adopted. Its per-entity containers (DynamicHashMap, thread streams) reorder entries or events, so they do not fit bit-exact state. BovineLabs Timeline (clip entities, top-4 weighted blend) is a cutscene design, not one for hundreds of timelines per character.
- Resolve per-clip data once, not per frame (the idea behind BovineLabs Timeline's baked clip entities): tl.unity's kind entries cache a window index into a contiguous copy of the library's single-stage steps (`KindIndex.WindowSteps`, bounds-checked) and trust it only while the chunk's change version and the index identity match the tick job's stamp. Kind jobs 18-21 % faster at 20,000 x 200 (7000.0.0a16, Burst). A first version packed the low 32 bits of the step pointer and rebuilt it from shared high bits; steps are allocated per timeline, so the high bits did not always match and a packs-mode run failed: never pack pointers by assuming one allocation. Refresh every cache on a library change and test it by republishing from a second library loaded from the same bytes. `[NoAlias]` on the generated jobs' column pointer parameters measured 0 %.
- Derive the live clips from playback state and a baked table instead of keeping per-clip entries (IAFahim/tl#651, tl.unity `perf/651-score-tables`, 7000.0.0a16, 11 workers, owner shape 500 timelines x 16 tracks x 30-60 ticks with blends). Which clips are live at local tick t of a timeline, their blend factor and their fold value are bake-time constants, so one row per (timeline, tick, kind) lists them, and the kind kernel reads each slot's (timeline, tick). Playback stepping then runs kind-free: no entry appends, no `RemoveSpan`, no events per clip. 50,000 characters x 100 active timelines x 8 live tracks went from 312 ms to 49 ms (scalar), and to 29 ms with an AVX2 lane kernel plus frames baked after the user's `Blend` (10.8x). The tick job fell from 74 ms to 2 ms, and heap per character from 21.5 KB to 1.2 KB, plus one 2-6 MB shared table. Everything stayed bit-equal every tick. The per-entry design had cost 371 instructions and 2.6 last-level-cache misses per live clip per tick (`perf stat`), and 39 % of its entries were idle blend windows (a blend track bakes 3 windows: clip A, the union and clip B). With 16 tracks almost no window sits in one stage, so a single-stage step cache never applies.
- SIMD across characters in Burst 2.0.0 (in-engine, intrinsics up to AVX2/FMA, no AVX-512 class): make the lanes characters and let each lane walk its own feeds in Combine order. That keeps float sums and last-wins ties bit-exact. Do the gathers (slot words, table starts, fold values) with explicit `X86.Avx2.mm256_mask_i32gather_epi32` or `_ps` and store them with one 256-bit store to a stack array. Run the user's `Evaluate` and `Combine` in a loop over those contiguous lane arrays with `Unity.Burst.CompilerServices.Loop.ExpectVectorized()`. `perf annotate` shows `vmulps`/`vaddps`/`vmaskmovps` on ymm. Keep a scalar twin under `if (!X86.Avx2.IsAvx2Supported)`; managed code runs it. Address 8 separate `DynamicBuffer` heap blocks as 32-bit dword offsets from one lane's base, range-checked with a scalar fallback, so one `i32gather` reads them.
- One baked row per active timeline, not per clip (IAFahim/tl#651 row spike, tl.unity `dced3c4`, 7000.0.0a16, 11 workers, Ryzen 5 8500G, one run per cell, synthetic rows at the owner shape).
  - **Layout.** Bake each (timeline, tick) into one 32 B row of 8 lanes holding every kind's combined value. An active timeline is a 2 B origin, so `row = origin + frame`. Accumulate is one aligned load plus `vpaddd`/`vpmaxsd` per active timeline.
  - **Speed.** 0.63 ms at 50,000 x 100 active timelines and 12.3 ms at 1M x 100. That equals a C `-O3 -mavx2` OpenMP loop doing the same work, so Burst reached the hardware floor here.
  - **What cost 1.56x.** Extracting a per-element flag with scalar code (`vmovmskps` + shift + or) was 6 of 13 loop instructions in `perf annotate`. Make the flag a property of the index instead: rows end on 64-row blocks, and `(origin + frame) & 63 == 63` is three SIMD ops for 16 origins.
  - **Order-free, identical hosts.** Integer and max lanes are commutative, so the result is independent of slot order, and a reverse-order managed reference stayed bit-equal for 130 ticks. A .NET 10 `Vector256` twin printed the same state hashes as Burst.
  - **ECS vs flat arrays at 1M.** The Burst ECS version (fused job, `ComponentLookup` to a random target entity) took 21.9 ms; the flat-array .NET twin took 14.6-15.9 ms. Float vs integer lanes made no speed difference (0.95 vs 0.99 ms at 50k).
