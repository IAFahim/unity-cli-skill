# Unity field notes for agents

Read once, top to bottom. Every line cost someone hours.

## Owner rules (every agent, every brief starts with rule 1)

1. **Before any work** pull this repo (`git -C <clone of IAFahim/unity-cli-skill> pull --ff-only`, clone it if missing; see `references/new-pc-setup.md`) and read this file. **Before you finish**, push what you learned back to `main` here (one verified line in the right section; `CONTRIBUTING.md`).
2. **Newest Unity 7 editor only.** Install a newer one by name with the CLI (`unity install 7 --yes --accept-eula`); never test, pin or mention older versions. Scripts pick the newest installed editor.
3. **Finish and test locally first.** CI is not a priority; do not work on CI or runners unless asked.
4. **Direct pushes to `main` are authorized** in IAFahim repos (`git pull --rebase origin main`, `git push origin HEAD:main`, never `--force`).
5. **Manage, delegate, right-size**: strongest model for performance and diagnosis, a small one for mechanical work. One brief per agent with file ownership, own worktree; commit the shared skeleton before agents fork, and decide which assembly owns each linked file (duplicate public types = CS0433). Detail: `references/workflow.md`, `references/sv-v3-architecture-and-process.md` B4.
6. **One Unity process at a time**: take the lock directory (`mkdir _work/unity.lock` fails if held), remove it when Unity exits.
7. **Short reports** (commands, counts, shas, what is unverified). **No code comments** in these repos.
8. **Never hand-write or hand-edit Unity-serialized files** (`.asset`, `.unity`, `.prefab`, `.mat`, `.meta`, ProjectSettings YAML): it silently corrupts references (`fileID: 0`) and causes slow reimport loops. Create them through Unity: an editor script in the scratch project's `Assets/Editor` (never the package) run with `-batchmode -nographics -quit -executeMethod`, or a headless Editor driven by `unity command eval`. Verified recipes: `references/headless-assets.md`.
9. **Unity ECS: `ISystem`, `IJobEntity`/`IJobChunk`, Burst, unmanaged data only.** Never `SystemBase`, managed components, GameObject lookups or other managed or hard-coded workarounds. The whole Tl hot path and every lib we use is unmanaged; managed code only in editor tooling, authoring and bakers. Needing a workaround means Tl or the lib lacks something: stop, `gh issue create` in that repo (minimal repro, missing API), tell the owner. Detail: `references/unity-ecs-rules.md`.
10. **Designers wire references in the Inspector** (drag and drop on authoring components and ScriptableObjects). Never by name or path in runtime or authoring flow: no `AssetDatabase.Load*`, `Resources.Load`, Find-by-name. Only tests and editor-only tooling may.
11. **Any Unity task**: make sure the project's own `AGENTS.md`/`CLAUDE.md` has a "Start here" pointing to this skill plus these hard rules; add it if missing, commit, push.
12. Stuck after two honest attempts: `scripts/ask.sh "<question>" body.md` files a `question` issue (versions, repro, exact error, what you tried). The repo is public: no secrets or personal paths.
13. **Cross-machine work goes through GitHub issues, never the owner as relay.** Before starting, check open issues labelled with your OS (`gh issue list --repo IAFahim/<repo> --label <windows|linux>`). On a cross-machine problem open or comment on one with repro, expected vs actual, logs and the command that proves it; claim by commenting; post root cause and commit shas when fixed; the other machine verifies and comments the result. Example: IAFahim/tl#576 (Linux demo step 10).
14. **Code you show a person must read top to bottom without comments.** Assume they read only the code. Order it the way it runs (input, first step, next step, output), so no name points at something defined further down. Name every type, method and parameter by its role (`totalPushThisTick`, not `total`; `WindClipToPushThisTick`, not `Evaluate`). Give one complete file that compiles, never fragments, and run it before you show it: paste the real output, not what you expect. Where the library hides an order or a rule (who runs first, what must be on a different track), say it in the code or the names, then verify it. A vocabulary change (a rename) is done only when every place that uses the word changes together (attribute, JSON keys, docs, tests); decide the full list first, or do not start.
15. **Decide, do not ask.** The owner is not a relay or a tie-breaker for things a developer would simply do. A decision that is reversible, in scope and keeps public API and pinned hashes unchanged is yours: pick the safer option, write one line on the issue, continue. Ask only for tags, releases, visibility, deleting data you did not create, force pushes, public API or pinned-hash changes, budget waivers and licence. Act and report; do not leave easy work for the owner.
16. **A new implementation becomes viable through small developer fixes, then a gate.** Profile first (bounds checks, per-tick copies and allocations, rebuilding per tick what changes per membership change, indirect loads, managed arrays on a runtime path, JIT tier-up, quadratic setup). A rewrite replaces the old code only when, in the same harness and in Unity with Burst, it is at least 2x faster at the owner's scale, setup and memory are no worse, warm allocation is 0 B, hashes are bit-exact, no test was loosened, the source budget does not grow, a fresh clone compiles, and a second agent reran the numbers. Failed goals are never ticked as done. Detail and the 5.0 evidence: `references/new-implementation-viability.md`.
17. **You own issue lifecycle; the owner never babysits it. Talk before you file.** Issues come from agent work: a finding, a failed check, a design problem or a proof gap an agent hit (sv: `issues/NNNN-*.md` with a `Status: open|closed` line; other repos: `gh issue`). Never file an issue from a chat answer or a guess, and never because the owner described what they want: talk with them until the problem is understood, say what is or is not possible, and file only once it is clear. The owner does not read issues; the conversation comes first. When the work is done and a second run or agent has verified it, close it yourself: `Status: closed`, commit sha, receipt (test counts, digest, numbers with tag and settings). Reopen it yourself when a later change, a failing run or a new finding touches it. Before ending a task list what you closed, opened and reopened in one line; never ask the owner to open, close or check an issue.
18. **Know the thing before you touch it or manage others on it.** Before editing a library, or briefing an agent on it, you must be able to say in your own words what it is for, what it stores and where, how data moves through it, and what the owner means to build with it. Get that from the project's `AGENTS.md`, README, design and contract docs, the code, and the owner. Never from file names, a third party's plan alone, or a guess. A green test suite and a plan's checklist do not prove it is the thing the owner wants: check the work against the owner's intent. If you cannot state the purpose, or `AGENTS.md` does not say what the project is building and what it is, stop, say so, and get the owner's statement first. Every project's `AGENTS.md` opens with what it is, what it builds, the shape of its data and who uses it how. Agent briefs carry that understanding; an agent never starts from the task text alone. What a one-file senior brief and the standing code brief must contain, and what this rule cost when ignored: `references/sv-v3-architecture-and-process.md` Part B.
19. **Every library has one stated job, and every system is built as layers the owner can preview.** A layer is legitimate only with all five: one job in one sentence, named plain-data input and output types, a law testable alone, a readable dump (the owner previews by reading), and a slow reference form to diff against; otherwise it is ceremony, delete it. Libraries never reference each other; glue lives in the host; time is tl's, state is sv's, space is Gi's. Fuse layers in the compiler only when bit-identical, keep an `unfused` mode for previews, keep each project's layer table true in its `AGENTS.md` in the same commit. Roles, the sv v3 layer table and the trap: `references/layers-and-library-roles.md`.
20. **When stuck, search the web instead of trying a third guess.** Agents have WebSearch and WebFetch. The rule: after two failed attempts at the same problem, or before any step that depends on an outside fact (Unity 7 / CoreCLR / Burst behaviour, .NET 10 and C# 14 features, SIMD and intrinsics, sorting and cache techniques, a library's API, an error message you cannot explain), stop and search. Prefer official docs, release notes, Unity discussions threads, source repositories and issue trackers over blog summaries; quote the sentence you rely on and its URL in your notes or issue; mark anything not confirmed by an official source as unconfirmed. Search the exact error text first. Never search with the owner's name, email, project names or secrets, and never paste project code into a search. Project-specific design questions (what sv should mean, what the owner wants) are not for the web: read the project's docs or ask the owner (rule 18). Record what the search taught in the references when it will save the next agent time (rule 17 of the owner preferences: dense, early, no secrets).
21. **Making it human is THE step, not a step.** A proof of concept that works is not done until a designer can run, tune and extend it without a programmer; the fastest route for an agent is almost never the right route for a person. Before you call anything finished (even a three-file demo): (a) **one editable home per value.** Timing and motion live in the tl clip (curves are a `TlCurve` field, never a formula in a track), rules and state in the sv pack JSON, everything else in a **ScriptableObject grouped by who owns it** (World or level, Player or character, Presentation, Engine) and referenced from the authoring component in the Inspector. Code keeps only invariants (math identities, ids from generated enums). A named `const` is still hardcoded: never write one for anything a person might want to change (keys, speeds, reaches, counts, colours, camera offsets, font sizes, capacities, text). Input is an `InputActionReference` from a controls asset designers rebind, never `Keyboard.current.spaceKey`. (b) **One source of truth.** A builder, a baker and a runtime system read the same asset; copying a value into a second const (lane count in the coin builder and in the runner) is a silent desync. (c) **Authoring components hold references, not numbers**, and a baker calls `DependsOn` on every asset it reads (without it an edit never rebakes the SubScene) and, when a reference is missing, logs an error naming what to assign and bakes nothing; no fallback defaults in code. (d) **Builders load or create** every asset and never overwrite one a designer may have edited; they regenerate only derived content (scenes, placed objects). (e) **Say what a value means**: `[Header]`, `[Tooltip]` with the unit, `[Min]` and `[Range]`, a custom inspector warning for impossible combinations, gizmos for anything spatial. (f) **A designer guide** in the project lists what to change where, kept true in the same change as any new setting. (g) **Prove the wiring, not the move**: change each kind of asset (a number, a count, a reach to 0) and watch the behaviour change; "moved but not wired" is the false green here. Reference: tl-subway `Assets/Subway/Settings`, `Designer Guide.md`.
22. **Zero warnings from your own code, and Unity 7 is not the Unity you were trained on.** Compile errors are not the bar: finish only when the log has `error CS` = 0 **and** no `warning` lines from your own files (`grep -h 'warning [A-Z]*[0-9]*' log | grep Assets/`). A warning is a Unity 7 rule you have not met yet (statics cleanup UAL0010/UAL0013, OrderFirst/OrderLast ignoring ordering attributes, CoreCLR, C# 9 only, Entities 7 APIs, new Input System only): read the full message, find the rule (API summaries are in `<Editor>/Data/Managed/UnityEngine.xml`, real usage in `<Editor>/Data/Resources/PackageManager/BuiltInPackages/**` and `Library/PackageCache`, then the web, rule 20), fix the cause, and never suppress it, add `#pragma warning disable` or lower the analyzer severity. Read the whole warnings section of the compile log before reporting done, and put every new Unity 7 fact you learn here, verified, in the same push.
23. **State belongs to a world, never to a static.** ML training, servers, tests and Multiplayer Play Mode clones run many worlds in one process, so a mutable static is a bug the moment a second world exists, and code people read becomes the pattern they copy (a "short demo" with a static holder teaches the wrong habit). Where each kind of state goes: per entity, a component; per world, a singleton component or system state; a managed library object (an sv world, a native handle), published into the world through a handle entity and created and disposed by the same system (`OnCreate` or first `OnUpdate` creates, `OnDestroy` disposes and frees the GCHandle; without it every destroyed world leaks native memory); per view, the MonoBehaviour bound to one world (`Bind(World)`, default world only as the fallback); configuration, a read-only ScriptableObject (rule 21). Producers (a player, an AI agent, a test) write command components, so they are interchangeable; a runner without controls assigned is driven from outside, and that is the one allowed empty reference (say so in its tooltip). Statics are allowed only for pure functions with no fields, `const` invariants, generated code, and a registry that is explicitly process-wide, thread-safe and marked `[AutoStaticsCleanup]`. `World.DefaultGameObjectInjectionWorld` in gameplay code is the same smell. Proof is two worlds side by side: create a second `World`, add `DefaultWorldInitialization.GetAllSystems(WorldSystemFilterFlags.Default)` with `AddSystemsToRootLevelSystemGroups` and `ScriptBehaviourUpdateOrder.AppendWorldToCurrentPlayerLoop`, load the same SubScene with `SceneSystem.LoadSceneAsync(world.Unmanaged, guid, new SceneSystem.LoadParameters { AutoLoad = true })`, drive one world and check the other did not move, dispose one and check its library objects are released (verified on 7000.0.0a16: two sv worlds ran independently and the count of live sv worlds dropped from 2 to 1 on dispose).

## 1. First minute: look before you launch

```bash
pgrep -af '[U]nity/Hub/Editor|Editor/Unity' | cut -c1-200   # who is running, on which -projectPath
ls <project>/Temp/UnityLockfile 2>/dev/null                 # exists = that project is open
```

- **One Editor per project path, ever.** A second launch on the same path aborts ("another Unity instance is running"). Never kill an Editor you did not start; it is the person's.
- **Never open a windowed Editor yourself.** You cannot see it and it waits for focus. Run headless: batch mode (section 2), or a resident `-batchmode` Editor you drive with the CLI (section 7).
- Drive an Editor the person already has open (`unity command ...`) only when the task is about that Editor: its scene, its Inspector. Never enter Play mode in it, never focus its window and never capture its screen (see below).
- **Entering Play in a person's Editor steals their desktop (measured on Wayland with Hyprland, Unity 7000.0.0a16).** `unity command editor.playmode start` (it only sets `EditorApplication.isPlaying`; the Pipeline package makes no focus call) makes the Editor mark its window urgent, take focus and switch the person to its workspace within 0.1 s, whatever the Game view's Play Maximized / Focused setting (`PlayModeWindow.SetPlayModeFocused` was flipped both ways and made no difference). Measured safe: `script recompile` (focus is off unless you pass `--focus`), `editor.playmode stop`, every `-batchmode -nographics` run (no window is created, no focus event fires). So: verify behaviour with batch runs or a headless Editor; in the person's Editor compile, generate, leave the scene open and ask them to press Play; never `isPlaying = true` through `script run` either. Do not "restore" their workspace or focus afterwards: if they moved on it pulls them back again. To check a command for focus theft, listen on `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket2.sock` and look for `urgent`, `activewindow` and `workspace` events around it. Compositor-side suppression (a window rule with `suppress_event activate activatefocus` for the Unity window class) is the person's desktop config: offer it, never apply it unasked, and treat it as unconfirmed (workspace-switch cases are reported not to be fixed by it).
- The `unity-pipeline` skill's "Final checks" tell you to enter Play mode in the Editor; that step is overridden by the line above when the Editor belongs to a person.
- **Changing a project whose Editor is open (verified, 7000.0.0a16).** Writing over the file of a scene that Editor has open raises a modal "scene modified externally: Reload / Ignore" that blocks the whole Editor and every `unity command` (`editor status` says `blocked_by_dialog`); nothing over the CLI can answer it, and `NewScene`, `scene open` and the builder menu item can all stall behind it. Order of work: (1) `editor status` ready, stop Play, `scene list_open` and note dirty scenes; (2) leave any scene you will overwrite with `script run` calling `EditorSceneManager.NewScene(NewSceneSetup.EmptyScene, NewSceneMode.Single)` (it discards unsaved changes without asking, so stop and ask if the open scene is dirty and not yours); (3) packages first with `Client.Add(<url>)`, one at a time, wait for the lock file and `Library/PackageCache` entry; (4) then `.cs` files, then `script recompile` and poll `recompile_status` until `failed: false, errors: []` (`console status` keeps old error counts); (5) then assets, preferably generated by the live Editor (`script run` your builder's public method, never a menu item whose code calls `SaveCurrentModifiedScenesIfUserWantsTo`) instead of copied in; (6) after every write `editor status`, and `scene open` the scene again. Leaving the scene first and then copying its file produced no dialog.
- An on-disk `manifest.json` edit is not resolved by an Editor that is already open (the lock file and cache stay unchanged and the new assemblies are missing: CS0246 on their namespaces); use `Client.Add`.
- Settings in assets, verified on 7000.0.0a16 (Entities 7): a baker that reads a ScriptableObject and calls `DependsOn(asset)` rebakes the SubScene when that asset changes, with no manual reimport (a coin reach set to 0 in the asset gave 0 pickups on the next Play). `UnityObjectRef<InputActionReference>` in an `IComponentData` bakes and resolves in a non-Burst `ISystem` (`reference.action`, call `Enable()` once, `WasPressedThisFrame()`); build the controls asset from an editor script (`InputActionAsset.CreateInstance`, `AddActionMap`, `AddAction`, `AddBinding`, `File.WriteAllText(path, asset.ToJson())`, `ImportAsset`) and take the `InputActionReference` sub-assets with `LoadAllAssetsAtPath` by action name (editor tooling only). A `TlCurve` field on a clip shows as an `AnimationCurve` on the generated mirror and is evaluated with `frame.Clip.Arc.Evaluate(frame.Progress)`.
- `[UpdateBefore]` or `[UpdateAfter]` against a system or group that is `OrderFirst` or `OrderLast` is ignored with a warning in the log; to run earlier put the system in an earlier root group (`InitializationSystemGroup`). Entities Graphics deformation systems throw during world creation under `-nographics`; that is noise, not your bug. Timelines imported before their generated clip type compiles log `Missing types referenced from component TlTrack`; force reimport them after the compile.

## 2. Batch mode: compile, test, build, run code

`scripts/unity-batch.sh <project> <op>...` wraps this and prints one line per op: `exit errorCS passed/failed`.

```bash
U=<newest ~/Unity/Hub/Editor/*/Editor/Unity>
$U -batchmode -nographics -projectPath /abs/p -runTests -testPlatform EditMode -testResults /abs/r.xml -logFile /abs/r.log   # NO -quit with -runTests
$U -batchmode -nographics -quit -projectPath /abs/p -executeMethod Ns.Class.Method -logFile /abs/m.log                     # -quit for executeMethod
$U -batchmode -nographics -quit -projectPath /abs/p -logFile /abs/c.log                                                  # compile only
```

- Exit codes: 0 ok, 2 tests failed, 1 error (compile error, exception, license). Read them directly; **`| tail` eats the exit code.**
- **Always absolute paths** for `-testResults` and `-logFile`. A relative `-testResults` is resolved against the project, writes elsewhere, and you read a stale XML.
- Proof = `grep -c 'error CS' log` is 0, no own-code `warning` lines (rule 22) **and** the XML `<test-run total passed failed>` counts are what you expect. "exit 0" alone is not proof.
- First import of a fresh project takes minutes; later runs take ~1 min. Run long ops in the background and do other work; don't poll in a loop.
- PlayMode tests run in the same batch Editor. Frames are ~1 ms there: **wait on wall-clock time** (`Time.realtimeSinceStartup`), never on a frame count, for subscene streaming or FixedStep ticks.
- New Input System keys queued from an `-executeMethod` probe (`InputSystem.QueueStateEvent`) reach the game (`Update` and an `ISystem` alike, `wasPressedThisFrame` works) only after both `InputSystem.settings.backgroundBehavior = InputSettings.BackgroundBehavior.IgnoreFocus` and `InputSystem.settings.editorInputBehaviorInPlayMode = InputSettings.EditorInputBehaviorInPlayMode.AllDeviceInputAlwaysGoesToGameView` (batch has no Game View, so keys stay in the editor buffer and `isPressed` reads true only in `EditorApplication.update`). Verified Input System 7.0.0, Unity 7000.0.0a16: arrow keys and A/D moved a Tl lane runner; wait until the SubScene entity exists before the first key.
- A batch Play probe dies silently if the Editor recompiles during Play (log line `Requested script compilation because: AssetDatabase observed changes in script compilation related files`): statics, `EditorApplication.update` and `logMessageReceived` handlers vanish while the game keeps running. Run a plain `-quit` compile after every build or generate step and only then the probe; a probe that stops writing is a reload, not a hang (Unity 7000.0.0a16).
- A tl track can hold a `[Feeds(typeof(Kind))]` span method and a `[Pulse(typeof(Kind2), On = ClipEvent.End)]` method together: the span feeds a `[TlState]` column every tick (a jump arc `4 * height * progress * (1 - progress)`), the End pulse fires once; the consuming system must zero the column each tick (verified in Unity 7000.0.0a16 with Tl.Unity playback).
- CoreCLR player (Unity 7): `PlayerSettings.SetScriptingBackend(NamedBuildTarget.Standalone, ScriptingImplementation.CoreCLR)` (enum values on 7000.0.0a16: `Mono2x, IL2CPP, WinRTDotNET, CoreCLR`); the build folder has `Managed/` and `CoreCLR/`, an IL2CPP one has `GameAssembly.dll`. Both Windows variations ship with the editor. SubScenes bake at build time with no extra step (Force demo verified on both backends). On CoreCLR (runtime `.NET 10.x` with `Avx2`/`AvxVnni`), eager `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` Burst installers can preempt lazy `.NET 10` sidecars; give runtime `.NET 10` sidecars priority via coarse `[UnmanagedCallersOnly]` entrypoints (`references/burst-performance.md`).
- IL2CPP / Standalone player: `BuildPipeline.BuildPlayer` `locationPathName` must be the **executable file path** (not an existing directory, which fails with `"The target path ... already exists as a directory"`) from an `-executeMethod`, then run `./Game.x86_64 -batchmode -nographics -logFile /abs/p.log` and grep your own result line; call `Application.Quit(code)` in the player.
- CLI form: `unity test <project> --editor-path <Editor/Unity> --mode EditMode --filter Class.Method --output /abs/r.xml -- -logFile /abs/l.log` (exit codes in `references/windows-and-ci.md`).

Windows, CI and runner notes: `references/windows-and-ci.md`. How releases publish: `references/release.md`.

## 3. One scratch project, reused, cleaned

- Make **one** test project per Unity version, and reuse it. Point it at the package you are changing with `"com.x": "file:/abs/path/to/checkout/com.x"` plus `"testables": ["com.x"]` in `Packages/manifest.json`. **Never copy the package** into the project: copies drift and you test old code.
- Switch branches by repointing the `file:` path; the warm `Library/` makes the next run fast.
- Scratch helper scripts go in the scratch project's `Assets/`, never in the package. Delete them when done.
- **Test the package the way a user installs it**: a fresh project whose only dependency is the package. If it compiles only because something sits in your scratch `Assets/`, the package is broken. Ship what it needs, for example a vendored assembly with an asmdef and a sync script that has a `--check` mode.
- A vendored dll's `--check` must not compare rebuilt bytes: the same sources give different bytes per SDK, OS and checkout line endings (`core.autocrlf`). Commit a stamp of the pinned submodule commit, a CR-stripped `git hash-object --stdin` hash of the sources and the dll hashes, and compare that. Merging two branches that both rebuilt such dlls (cherry-pick conflict on `*.dll` + stamp): `git checkout --ours` the dlls and stamp, rerun the build script (it rewrites the stamp from the merged sources), then `--check`; regenerate auto-merged generated snapshots with the repo's tool and compare with `diff --strip-trailing-cr` (`cmp` differs under `core.autocrlf`). Never hand-merge either (tl.unity perf/int-unity, S4+S5).
- To prove a committed generator dll was built from its sources when your rebuild gives other bytes (`PathMap` embeds the checkout root), dump both dlls with `System.Reflection.Metadata` and diff the sorted lists: every user string (`MetadataTokens.UserStringHandle(1)`, then `GetNextHandle`) plus every method with its IL body size. Rebuilding tl.unity's `Tl.Gen.Unity.dll` in a second clone gave different bytes and 0 metadata differences, and against the old main only the changed string literals differed (tl.unity#45).
- A new git worktree has **empty submodules**: `git submodule update --init --reference <local clone> <path>`; the reference must be the main clone, not a linked worktree ("reference repository ... as a linked checkout is not supported yet"). If the pinned commit exists only locally (unpushed), use `git -c protocol.file.allow=always -c submodule.<path>.url=<local clone> submodule update --init <path>` (without `protocol.file.allow`: `transport 'file' not allowed`). `git submodule status` then still prints `-` (the url lives only in `-c`, not in `.git/config`) although the pinned commit is checked out; check with `git -C <path> rev-parse HEAD`.
- **Clean up before you finish**: delete `Builds/`, scratch projects you created, stale copies, and IL2CPP output (`Library/Bee`, `Library/Il2cppBuildCache`). Check `df -h /tmp ~` first and last. A test project is ~3 GB; an IL2CPP build adds 1-2 GB.

## 4. False greens (each one has fooled an agent)

- **Stale domain**: one compile error anywhere keeps the old assemblies loaded, so old code runs and old test counts appear. Check `error CS` = 0 before trusting anything.
- **Console is not the log**: `console get` can be empty while `Editor.log` (or your `-logFile`) has the errors. Read the log.
- **Stale source generator after a rebuild**: when a package's Roslyn generator dll is rebuilt in place (tl.unity `eng/build-generators.sh`), the next batch run can recompile the assemblies (`CacheMiss` in the log) with the previous generator still loaded in Unity's long-lived `VBCSCompiler` server, so the old generated code runs. A deliberately broken generator passed its tests once and failed on the next run (verified 7000.0.0a20, Windows). Kill `VBCSCompiler` (`Stop-Process -Name VBCSCompiler`) after every generator rebuild and before the Unity run that must see it; a negative control is only valid after that.
- **Stale bakes**: subscenes serve old baked data. After changing a baker or authoring asset, force reimport (`AssetDatabase.ImportAsset(p, ForceUpdate | ForceSynchronousImport)`) and check one baked component exists in the live world.
- **Hand-built worlds prove little**: a test that builds a `World` and calls `system.Update()` by hand skips auto-created systems, group order and singletons. Prove the default world at least once (a PlayMode test that loads a scene with a SubScene).
- **Ask the Editor, not the YAML**: inherited prefab components and overrides are invisible in files. Cross-prefab references serialize to `{fileID: 0}` without a warning.
- Never delete scene or prefab content to silence an error.
- **A kind's `Idle` method** runs in Unity since tl.unity 939a8fb (generator pin tl 434d729, IAFahim/tl#590); before that it was silently ignored (no error, no warning) and a "can double jump" flag stayed true after its clip while the .NET host reset it. With an older tl.unity use the portable form: a clip with the "off" value from the end of the first clip to the end of the timeline (nothing writes the column after the last clip). Verified both ways in Unity 7000.0.0a16 PlayMode.
- **A Git-URL UPM package cannot pull a Git-URL dependency**: a package.json dependency on a package that lives only in Git fails `Package [x@0.1.0] cannot be found`; the install doc must list that dependency's Git URL in the project manifest too. Linux FBX Exporter without `libxml2.so.2` throws a `DllNotFoundException` that lists only CoreCLR search paths for `UnityFbxSdkNative`, never libxml2; probe the dependency with `dlopen` to name it. Test real-asset suites that `Assert.Ignore` without their assets on a copy project before a release: one hid a sampling change for weeks.
